# Project Status

Snapshot of what exists in this repo today, for planning purposes. Update this file at the start of each new phase rather than trusting it to stay accurate on its own — treat it as a snapshot, not a live doc. See [`PRODUCT_VISION.md`](PRODUCT_VISION.md) for where the product is headed.

Last updated: 2026-07-16 (Phase 11.5C complete).

## Tech stack

- **Framework:** Next.js 16.2.10 (App Router, Turbopack), React 19, TypeScript
- **Styling:** Tailwind CSS v4
- **Database:** MongoDB Atlas via Mongoose (migrated off PostgreSQL/Prisma between Phase 4 and Phase 5 — no migration files; schemas are defined directly in `src/models/*.ts`). Every model uses a random UUID string as `_id` (via the shared `idField` helper), so `.id` behaves like the old Prisma cuid ids. `src/lib/mongodb.ts` pre-resolves `mongodb+srv://` DNS SRV/TXT records with an isolated resolver before connecting — works around networks whose default resolver can't answer SRV queries, and around Turbopack Server Action bundles not reliably sharing global `dns.setServers()` state.
- **Auth:** Auth.js v5 (`next-auth@5.0.0-beta.31`), Credentials provider (email/password, bcrypt-hashed), JWT sessions
- **AI:** Anthropic Claude (`@anthropic-ai/sdk`) — structured JSON-schema outputs, used for website-analysis extraction, product/service discovery, Business Brain synthesis, competitor identification, search-query generation, customer extraction (Phase 7), project extraction (Phase 9), tender buyer/opportunity extraction (Phase 10), vendor registration extraction (Phase 11), and public contact extraction (Phase 11.5B). **Not OpenAI** — every phase's spec since Phase 7 has called for OpenAI, but this codebase has used Anthropic exclusively since Phase 1; introducing a second, largely-duplicate AI provider would be the kind of unnecessary complexity this project has consistently avoided, so `extractCustomerCandidateAI`/`extractProjectCandidateAI`/`extractTenderCandidateAI`/`extractVendorRegistrationCandidateAI`/`extractPublicContactsAI` all follow the same mock-or-Anthropic dispatch as every other extractor instead. All AI extraction goes through `src/lib/ai-extraction` (`isMockAIEnabled()`), which falls back to deterministic no-network mock extractors whenever `ANTHROPIC_API_KEY` is unset or `ENABLE_MOCK_AI=true` — the app is fully exercisable end-to-end without a real key.
- **Search:** Pluggable provider abstraction (`src/lib/search`) — Tavily, Exa, Bing, Google CSE, SerpApi, or a no-key Mock provider (default when unset)
- **Billing:** Stripe (`stripe` SDK) — hosted Checkout (`src/lib/billing/checkout.ts`) + webhook receiver (`POST /api/webhooks/stripe`). Degrades gracefully without `STRIPE_SECRET_KEY`.
- **Email:** Resend (`src/lib/email`) — mock-or-real provider pattern; `RESEND_API_KEY` unset falls back to a no-network mock provider that logs instead of sending.
- **Package manager:** npm (`package-lock.json` present; no yarn/pnpm lockfile)
- **Deployment target:** Vercel — `vercel.json` configures `/api/cron/discovery` and `/api/cron/discovery-run`
- **Test framework:** [Vitest](https://vitest.dev) — two configs: `vitest.config.ts` (node environment, `*.test.ts`, real MongoDB Atlas, sequential file execution since tests share one database) and `vitest.component.config.ts` (jsdom + React Testing Library, `*.test.tsx`). `npm test` runs both.

## Folder structure

```
src/
  app/                  Next.js App Router pages (see Routes below)
  components/           UI, by feature area (business-brain, company-profile,
                         customers, dashboard, discovery, landing,
                         onboarding, product-discovery, ui/)
  config/               site.ts (nav/site name), onboarding.ts (step config)
  lib/                  Business logic — one folder per feature/service, plus
                         actions/ (server actions) and validations/ (Zod schemas)
  models/               Mongoose schemas + types, one file per domain area,
                         re-exported from models/index.ts
  instrumentation.ts     Runs validateEnv() on server start
  auth.ts                Auth.js config
  proxy.ts               Optimistic-auth redirect (Next.js 16 proxy, replaces middleware.ts)
scripts/
  check-workspace-scoping.mjs   Fails if a model is missing workspaceId
```

`changeContactStatusAction`, `addContactActivityAction`, `linkContactAction`, `deleteOrArchiveContactAction` — plain typed-argument actions, mirroring every other phase's status/link actions), (Phase 11.5B) `src/lib/actions/contact-discovery.ts` (`generateContactDiscoveryTargetsAction`, `generateContactSearchQueueAction`, `runContactSearchAction`, `processContactResultsAction`, `runPublicContactDiscoveryBatchAction` — a composite action that runs all four steps in sequence, each independently toggleable and independently callable via the dedicated actions, collecting per-step failures as warnings rather than aborting the whole batch, `updateContactDiscoveryTargetStatusAction`), and (new, Phase 11.5C) `src/lib/actions/contacts.ts` extended with `refreshContactEnrichmentAction`/`refreshWorkspaceContactEnrichmentAction`/`markContactDoNotContactAction`/`removeContactDoNotContactAction`/`assignContactOwnerAction`/`assignContactToUserAction`, plus two new files: `src/lib/actions/contact-tasks.ts` (`createContactTaskAction`, `updateContactTaskAction`, `completeContactTaskAction`, `generateRecommendedContactTasksAction`, `generateMissingContactTasksForWorkspaceAction`) and `src/lib/actions/contact-email-templates.ts` (`createContactEmailTemplateAction`, `updateContactEmailTemplateAction`, `deleteContactEmailTemplateAction`, `seedDefaultContactEmailTemplatesAction`, `generateContactEmailDraftAction`, `logContactEmailDraftAction` — the last logs a `ContactActivity` only when a user explicitly saves a generated draft; nothing in either file sends an email or a notification) — exports use plain `GET` API routes instead of server actions (a server action can't trigger a browser file download without extra client-side blob-handling JS; a plain `<a href>` to a route with `Content-Disposition: attachment` does it with zero JS, matching the pre-existing `/api/export/products`/`/api/export/target-companies` pattern) — everything else stays a server action, not a REST endpoint.

### Two target-discovery pipelines (deliberate, not an oversight)

This codebase now contains **two** ways a "discovered target" gets created:

1. **`TargetCompany`** (Phase 3/4) — `src/lib/target-companies/service.ts`'s `discoverAndExtractTargetCompanies()` runs stored `SearchQuery` rows straight through the Search Service and Claude in one call, no persisted raw-results step. Still fully functional (`RunDiscoveryButton`/`AddTargetCompanyDialog` components, lead scoring in `src/lib/lead-scoring/`), but as of Phase 7 it is **not linked from any page** — `/dashboard/customers` was repointed to the new pipeline below.
2. **`TargetCustomer`** (Phase 5+6+7) — the Discovery Brain generates a persistent Search Queue → the Search Execution Engine runs it and stores `RawSearchResult` rows → `src/lib/customers/processor.ts`'s `processCustomerResults()` extracts, scores, and dedup-checks each result into a `TargetCustomer`. This is what `/dashboard/customers` shows and what the dashboard's Customers card summarizes.

Nothing was deleted — the older model/service/components are untouched and still pass their existing tests — but they're effectively legacy now that the richer, raw-results-backed pipeline covers the same need. Worth an explicit decision in a future phase: retire pipeline 1 outright, or keep it as a manual "quick add" path alongside continuous discovery.

## Test database cleanup guard

`src/lib/test-utils/cleanup-orphaned-records.ts` fixes the orphaned-`BusinessBrain` accumulation described in "Current risks" history below. It:

- **Only ever runs under `NODE_ENV=test` (Vitest sets this automatically) or an explicit `ALLOW_TEST_DB_CLEANUP=true` opt-in** — `isTestDbCleanupAllowed()` is checked first and `cleanupOrphanedTestRecords()` throws `TestDbCleanupNotAllowedError` (deleting nothing) if neither is true. **No production/staging/real-user-data cleanup was performed or is possible through this utility** — there is no code path that bypasses the guard.
- Finds every `Workspace` that still exists, then deletes `BusinessBrain` rows (and the same-shaped debris in `DiscoveryBrain`, `SearchSource`, `SearchQuery`, `SearchQueueItem`, `CountryCoverage`, `IndustryCoverage`, `ProductCoverage`, `SourceCoverage`, `CoverageSnapshot`, `DiscoveryStrategy`, `DiscoveryRun`, `DiscoveryRunItem`, `SearchProviderLog`, `DiscoveryErrorLog`, `RawSearchResult`, `TargetCustomer`, `ProjectOpportunity`, `DuplicateRecord`, `MergeHistory`, `SourceHistory`) whose `workspaceId` doesn't match any of them — never touches a row belonging to a still-live workspace.
- Logs how many orphaned `BusinessBrain` rows were found/deleted/skipped, which guard let it run, and a per-model count of related rows deleted.
- Is wired into `src/lib/discovery/service.test.ts`'s `beforeAll` (sweeps historical debris before the one test that scans every ACTIVE/STALE brain in the shared database) and `afterAll` (sweeps this run's own newly-orphaned rows immediately, instead of leaving them for next time).

Running it against the shared test database found and deleted the ~140 orphaned `BusinessBrain` rows (plus their related debris) that had accumulated since Phase 4 — verified via a one-off diagnostic query showing 0 orphaned brains remain. `runDiscoveryForAllWorkspaces processes only workspaces with an ACTIVE/STALE brain` went from timing out at 300s back down to running in well under 15s; its timeout was reduced to 60s accordingly.

## Current risks

- **The real (non-mock) Claude path is configured but unusable in this environment** — the Anthropic account is out of credits (see "Verifying the real Claude integration"). Doesn't affect the dedup engine itself (no AI calls — pure string/field comparison), but does affect the customer/project/tender/vendor-registration extraction that feeds it.
- **No rate limiting on customer/project/tender/vendor-registration processing or deduplication** beyond the batch-size caps (`src/lib/customers/constants.ts`, `src/lib/projects/constants.ts`, `src/lib/tenders/constants.ts`, `src/lib/vendor-registrations/constants.ts`, `DEDUP_SCAN_LIMIT` in `src/lib/dedup/constants.ts`) — repeated manual runs could burn through AI quota (extraction) or CPU (the O(n²) dedup scan) once real usage scales up.
- **The deduplication scan is simple O(n²) pairwise comparison, capped at `DEDUP_SCAN_LIMIT` (200) records** — fine at MVP scale; a workspace with thousands of records in any one entity would need a candidate-blocking index (e.g. by domain/link/name prefix) instead of comparing every pair, or `run*Deduplication` would silently only ever compare its first 200 (oldest-first) records.
- **`brainFeedback` scoring factor is a placeholder** on `TargetCustomer` and `ProjectOpportunity` scoring (weight 0) — Mark Good Fit/Bad Fit and Mark High Potential/Not Relevant already write to `BrainFeedback`, but nothing feeds that signal back into future scoring runs yet. `TenderOpportunity` scoring has no `brainFeedback` factor at all yet.
- **`TenderBuyer` and `VendorRegistration` have no scoring/priority** — by design (both are reviewed like customer records, not prioritized like tender/project opportunities), but worth confirming this still matches the product vision as volume grows.
- **`Contact` scoring's `isLinkedToApprovedRecord` factor is recomputed on every write, not event-driven** — `rescoreContact()` re-checks all five related records' current status inside `createContact`/`updateContact`/`link*` every time, so a contact's score only updates when *that contact itself* is next touched, not the moment its related `TargetCustomer`/etc. flips to Approved. Fine at MVP scale (no background job re-scores idle contacts), but worth a periodic re-score job if this drifts noticeably in practice.
- **CSV exports are capped at `MAX_EXPORT_ROWS` (10,000 rows)** — an MVP limit (`src/lib/export/service.ts`); a workspace exceeding this on any one entity gets a silently-truncated (newest-first) export, not an error. No pagination/streaming for larger exports yet.
- **Reports have no caching/materialization** — every report on `/dashboard/reports` re-runs its aggregation queries on each page load; fine at MVP scale, would need a scheduled snapshot (writing to a new model) if report volume/complexity grows.
- Two parallel target-discovery pipelines exist (see above) — not itself a bug, but a real "which one is the real one" trap for a future developer who finds `TargetCompany` first.
- ~~Orphaned `BusinessBrain` rows accumulate in the shared test database~~ — **fixed** (see "Test database cleanup guard" below). `src/lib/test-utils/cleanup-orphaned-records.ts` sweeps `BusinessBrain` and 19 related workspace-scoped models whenever their `workspaceId` no longer matches a live `Workspace`, gated so it only ever runs under `NODE_ENV=test` or an explicit `ALLOW_TEST_DB_CLEANUP=true` opt-in. Wired into `src/lib/discovery/service.test.ts`'s `beforeAll`/`afterAll` (the one test that scans every ACTIVE/STALE brain in the whole database), which both fixed the ~140 rows of debris that had accumulated as of Phase 9 and stops it recurring. The test's timeout came back down from 300s to 60s once the sweep was in place.

- **What's functional:** Every `Contact` now carries a live-recomputed enrichment score/status/missing-fields/recommended-action/best-contact-for, refreshed automatically on every create/update/status-change/link/activity-log — no separate "run enrichment" step is required, though a manual "Refresh Enrichment" action exists for after a bulk change. `doNotContact`/`ownerUserId`/`assignedToUserId` are the only user-set CRM fields, and are guaranteed to survive every automatic enrichment refresh. The recommendations engine ranks the best contact to approach for any TargetCustomer/ProjectOpportunity/TenderBuyer/TenderOpportunity/VendorRegistration, flags missing recommended roles, and surfaces a clear alert ("No procurement contact found", "Only low-confidence contact available") when nothing good exists. `ContactTask` gives every contact (or, for a company with no contact at all yet, the bare entity) a follow-up to-do list, with overdue detection computed on read and a one-click workspace-wide "generate recommended tasks" sweep. `ContactEmailTemplate` + `generateContactEmailDraft` produce ready-to-edit subject/body text pulling in the contact's name/company/designation, whichever opportunity they're linked to, the workspace's own company name (from the Business Brain), and country — a human still has to copy it into their own email client and press send. The Contacts list/detail pages, the new Contact Tasks and Email Templates pages, every related-entity detail page, the main dashboard, the Reports page, and CSV exports all reflect the new CRM/enrichment data.
- **What is intentionally not built:** Email-sending automation — `generateContactEmailDraft`/`logContactEmailDraftAction` only ever produce and (optionally) log text; there is no Gmail/SMTP connection, no send button, and no scheduled/triggered send anywhere in this app. LinkedIn scraping/automation — still never built, same as Phase 11.5A/11.5B. Email verification — third-party APIs (Hunter/Apollo/Clearbit/ZoomInfo/Lusha/RocketReach or similar) are not called; `emailStatus` is still set manually or left `UNKNOWN`. Private/paid contact-database integrations — none added. Email guessing — no name-pattern-based guessing anywhere, in either the discovery pipeline or the new draft generator.
- **Known limitations:** `ContactTask.contactId` is optional specifically so an entity-level "find a contact" task can exist before any `Contact` does — callers that assume every task has a contact need to null-check it. `getBestContactsForEntity`'s ranking and `getWorkspaceContactCoverageSummary`'s "active entity" statuses are hardcoded per related-record type rather than configurable, mirroring the same tradeoff Phase 11.5B's target-generation prioritization made. `ContactTask`/`ContactEmailTemplate` intentionally duplicate a small amount of "which entity types are linkable, with which active statuses" configuration across `contacts/tasks.ts` and `contacts/recommendations.ts` rather than sharing one source of truth, to keep the two modules independently readable — a future refactor could extract this if the lists drift. `enrichmentScore`/`priorityScore` are two independently-weighted 0-100 scales measuring different things (data completeness vs. lead value) that can be confused at a glance; the UI labels them distinctly ("Enrichment score" vs. "Priority score") but nothing enforces that distinction at the type level. No rate limiting on the workspace-wide "Generate Recommended Tasks" sweep beyond its own internal batch caps (50 tasks per category per call). Reports have no caching, same as every prior phase.
